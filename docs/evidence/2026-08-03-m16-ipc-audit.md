# M16 — SysV IPC 와 auditallow, 그리고 "0" 이 측정이 아닌 경우

- **날짜**: 2026-08-03
- **기기**: MediaTek MT8775, Android 16, 커널 `6.1.145-android14`, `uid=10297 Seccomp=2`
- **목적**: 문서에 오래 남아 있던 `PENDING_DEVICE` 두 건을 실제로 재기

## 1. SysV IPC — 차단된다 (RISKS R9, 02-architecture §121)

두 문서 모두 "Termux 에서는 Android seccomp 에 막히지 않을 수도 있다, `alr doctor` P2 가 답한다" 로 남아 있었다. 잰 결과:

```
$ alr run /tmp/alripc            # tests/device/probe_ipc.c
shmget : Function not implemented
semget : Function not implemented
msgget : Function not implemented
```

`EPERM` 이 아니라 **`ENOSYS`** 라는 점이 중요하다. 같은 실행의 슈퍼바이저 로그가 이유를 말해 준다:

```
$ ALR_LOG=2 alr run /tmp/alripc | grep -c 'alr sigsys'
4
```

`set_robust_list` 1건 + IPC 3건. 즉 세 syscall 모두 zygote 필터에 걸려 `SECCOMP_RET_TRAP` → SIGSYS 로 오고, 우리 슈퍼바이저가 기본값 `-ENOSYS` 로 에뮬레이션한 것이다. **게스트 안에서 SysV IPC 는 쓸 수 없다.**

영향은 제한적이다 — 대상 워크로드 중 SysV IPC 를 쓰는 것이 없고, 쓰는 소프트웨어(일부 DBMS, X11 MIT-SHM)는 애초에 비목표다. `ENOSYS` 는 라이브러리들이 폴백 경로를 타게 하는 표준 신호이기도 하다.

## 2. auditallow 로그 볼륨 — 앱 안에서는 잴 수 없다 (RISKS R6)

[§B1/§B3](../01-platform-facts.md) 에 따르면 `untrusted_app_27` 도메인은 `execute` 와 `execute_no_trans` 양쪽에 `auditallow` 가 걸려 있어, 게스트의 모든 execve 와 모든 `.so` 매핑이 logd 에 레코드를 남긴다. exec 집약 워크로드에서 이것이 지배적 숨은 비용일 수 있다는 것이 R6 다.

재보려 했다:

```
$ logcat -b events -d | wc -l     # exec 6회 전후
0
```

**이 0 을 "오버헤드 없음" 으로 기록할 뻔했다.** 계측기를 확인하니 그게 아니었다:

```
$ logcat -b main   -d | wc -l     → 8
$ logcat -b events -d | wc -l     → 0      (에러 메시지도 없음)
```

`main` 은 내용이 있고 `events` 만 빈다. Android 는 events 버퍼를 권한 있는 리더에게만 연다. **0 줄은 권한 실패지 측정이 아니다.**

R6 는 계속 `PENDING_DEVICE` 다. 다만 막는 것이 무엇인지는 이제 안다: **외부 관찰자(adb)가 Termux 안에서 워크로드가 도는 동안 지켜봐야 한다.** 게스트 실행 자체는 반드시 실제 앱 컨텍스트여야 하지만(`uid>=10000 ∧ Seccomp=2`), 로그를 *읽는* 쪽은 adb 여도 유효하다 — 관찰이 실행 조건을 바꾸지 않기 때문이다.

## 3. 교훈

이 세션에서 세 번째다. **"없다" 는 관측은 계측기가 작동할 때만 증거다.**

- M15: `/proc` 접근 0건 → 트레이스가 배포되지 않은 빌드였다
- M14: 심볼을 뺐더니 php 가 고쳐짐 → 무관한 심볼을 빼도 재발했다
- M16: events 로그 0줄 → 버퍼를 읽을 권한이 없었다

세 번 모두 같은 처방으로 잡혔다: **결론을 내기 전에, 알려진 양성 대조로 계측기가 반응하는지 먼저 본다.** M16 에서는 `logcat -b main` 이 그 역할을 했다.
